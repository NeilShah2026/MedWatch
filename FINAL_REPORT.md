# MedWatch — Final report

Built end to end from `BUILD_SPEC.md` across 11 phases, each committed and pushed to
`claude/youthful-davinci-a3601n`. This report covers what was built, every test suite and its
result, the gaps, and what humans must review before real patients use it.

## Headline

- Everything in the spec is implemented: schema with RLS and audit, deterministic engines, synthetic
  seed with the five stories, auth with MFA and idle timeout, AI-tailored check-ins with rules
  fallback, patient/caregiver/nurse/admin screens, background jobs and alerts, docs.
- **The build session never had Supabase credentials.** The environment variables were added
  mid-session, and those only reach new sessions. So nothing has been pushed to the cloud dev project
  yet (`db:push`, `functions:deploy`, `secrets:sync`, `db:reset`), and the cloud-only suites are
  written but **not run**. To make up for this, the same code was verified against real
  PostgreSQL 16 (migrations, RLS, seed) and against an in-memory mock Supabase that runs the actual
  UI end to end with axe.

Bugs the verification layers caught and that were fixed: a per-row RLS function making the
dashboard take 5.1 s; `INSERT … RETURNING` failing under RLS for new patients; a trigger
referencing a missing record field; two WCAG contrast failures; a checkbox that never reached the
form state; a missing error boundary; a dev-server reload during PDF export; three user-facing
strings with banned wording ("You have been signed out", "not diagnoses", plus a test fixture).

## Known gaps

1. **Cloud not provisioned from this session**: run the first-time setup in the README in a new
   session with the variables set, then run `npm run test` (cloud RLS) and `npm run test:e2e`.
2. **Edge Function deployment of files outside `supabase/functions`**: functions import
   `packages/core` and `rules/*.json` by relative path. `deno check` passes, but whether
   `supabase functions deploy --use-api` bundles them must be confirmed on first deploy. If it does
   not, add a pre-deploy copy step in `scripts/functions-deploy.mjs` (see DECISIONS.md).
3. **pg_net / cron** need `npm run secrets:sync` (Vault). Until then only web-app-initiated runs happen.
4. **Mock-backed UI tests** emulate PostgREST/RLS. They prove the UI flows and accessibility, not
   the security boundary (that is proven on Postgres and by the cloud suites).
5. **Dependency advisories**: production has React Router v6 (moderate; v6 is required by the spec).
   The other 17 are dev-only tooling (Vitest's worker pool, Tailwind 3's toolchain).
6. **SMS** is console-only until Twilio credentials and a BAA exist. Delivery receipts are not tracked.
7. **CSP** allows `*.supabase.co`; pin it to the production project.
8. **Placeholder content**: all rules, scoring constants and the AI prompt are illustrative; legal
   pages are drafts.
9. Not built (not in spec): push notifications, offline mode, i18n beyond the `copy/` structure,
   EHR integration.

## What a human must review before real patients use it

1. **Clinical**: every rule file, the flag scoring constants (`packages/core/src/flags.ts`), the
   adherence thresholds, the symptom catalog wording, and the check-in prompt
   (`supabase/functions/_shared/prompts/checkin_v1.ts`). Change rule `status` to
   `CLINICIAN_APPROVED` only after sign-off (see docs/CLINICAL_RULES.md).
2. **Legal**: privacy policy, terms of use, and consent documents (all marked DRAFT); BAAs with
   Supabase (HIPAA add-on), the AI gateway/model provider and the SMS vendor.
3. **Security**: independent review of RLS policies and guard triggers, Edge Function auth, CSP;
   penetration test; MFA required for all staff; remove demo accounts; backups/PITR; incident
   response plan.
4. **Operations**: separate production Supabase project; `VITE_APP_ENV=production` (hides the demo
   banner); seed/reset never run in production (the scripts refuse).
